Architecture

How evrd fits together

One Go process holds your IRC connections and serves your clients. Run it on its own with a file on disk, next to Postgres and ScyllaDB, or as a cluster of nodes that share the work and take over when one fails.

01 · Components

One process, three kinds of storage

Native clients attach to the IRC listener, while the web app talks to the HTTP and WebSocket API. Both share the connection to each upstream network. Accounts go to a SQL database, chat history to a separate store, and metrics out over OpenTelemetry.

Why history has its own store

Chat history never goes into Postgres. The history directive picks the backend:

  • ScyllaDB, shared by every node. Each buffer gets one partition per month, read newest first. Writes are queued, so a slow database never stalls IRC.
  • Pebble, an embedded store on local disk, for one evrd process per directory.

evrctl history copy <from> <to> moves history between them.

03 · Request routing

Any node is a front door

In a cluster each user is owned by exactly one node, which runs their networks and serves their clients. A client can land on any node, and that node forwards it to the owner. Nodes need no message bus, only one extra hop.

The client connects to the balancer

The balancer passes IRC through as plain TCP, so TLS on 6697 terminates at evrd. It can't route by user, because IRC only reveals the username in PASS once the connection is already open.

any node

Any node answers

node-b accepts the connection, answers CAP and reads the registration: PASS, NICK and USER.

rendezvous

Find the owner

Every node computes the same owner by rendezvous-hashing the user ID over the live nodes, and Postgres holds the lease that confirms it. When a node joins or leaves, only about 1/N of users move.

EVRD-PROXY

Splice to the owner

node-b connects to node-a's internal IRC port, sends EVRD-PROXY <secret> <client ip> <caps>, replays the registration and any bytes already received, then splices the two sockets. node-a authenticates alice as usual. For the web app, pages that only need the database are served locally. The chat WebSocket, connect and disconnect, and *status are reverse-proxied to the owner's internal HTTP port.

04 · Failover

When a node goes away

Ownership is a lease in Postgres. Nodes heartbeat every 5 s and count as live if they beat within 15 s. Leases last 20 s. Step through a crash, or switch to a rolling deploy, where the node drains on SIGTERM instead.

Client

Balancer
Load balancerhealth checks · 2s connect
Nodes

Libera.Chatalice's upstream
Postgresuser_leases · TTL 20s
t = 0

Normal operation

node-a owns alice. It runs her Libera.Chat connection, serves her HexChat and renews her lease with one batched statement per heartbeat.

t = 0 s

node-a dies

Alice's upstream connection and her client connection drop with it. The balancer's short connect timeout and passive health checks take node-a out of rotation, so new connections don't wait a minute on a dead node.

SIGTERM

node-a drains

On SIGTERM a node stops its users' connections and releases their leases straight away, instead of letting them run out.

t ≤ 20 s

The lease expires, node-b takes over

Once alice's lease passes its TTL, the next node in her rendezvous order acquires it with a conditional update and bumps the epoch. The internal API refuses late requests from the old owner.

t ≤ 5 s

The next tick picks her up

Because the lease was released rather than left to expire, node-b acquires alice on its next tick, within 5 s, and starts reconnecting her networks at the paced connect_rate.

≈ 19 s

Back online on node-b

On the dev stack, after a docker kill of a node, a user's network was connected again on the other node 19 s later. Alice's client reconnects through any node and lands on the new owner. Networks see a disconnect and a reconnect, because a TCP connection to an IRC server can't move between machines.

deployed

node-a comes back empty

node-b now owns alice. When the new node-a starts, gradual rebalancing (at most 50 users per tick, once the node has been up 10 s) moves its share of users back over time.

Fencing: a node that can't renew its leases, for example because it lost Postgres, stops its users' connections at half the TTL, before anyone else may take over. Two nodes never hold the same nick on a network. A short Postgres outage is better than split-brain.

05 · Outbound addresses

Give every user an address of their own

Large networks throttle and cap connections per source address. Without help, every user on a node would connect to Libera.Chat from that node's single address.

Node
node-aconnect_rate 5
upstream_prefix6 2001:db8:42::/64
alice2001:db8:42::a1f3
bob2001:db8:42::7c20
carol2001:db8:42::e911 · paced
Network
Libera.Chatsees 3 addresses
Addresses come from the 2001:db8::/32 documentation range. A user always connects from the same address.
evrd.conf · per node
connect_rate     5                       # most connects/second to one server, per node
upstream_bind    192.0.2.10 192.0.2.11   # spread users over these (stable per user)
upstream_prefix6 2001:db8:42::/64        # or: an IPv6 address for every user
bindhost         192.0.2.20 vhost.example.org   # addresses users may pick

# a prefix needs Linux and a local route:
ip -6 route add local 2001:db8:42::/64 dev lo

What each one does

  • connect_rate spaces connects to each IRC server host per node, and reconnect backoff is jittered, so a takeover or netsplit recovery doesn't flood a network.
  • upstream_bind spreads users over a list of source addresses, with each user keeping the same one.
  • upstream_prefix6 gives every user their own IPv6 address from a routed prefix.
  • bindhost is ZNC's BindHost. It lists addresses users may choose from, and admins can lock a user's choice.

Per-address caps on large networks are usually the first real limit. Talk to the networks you care about about limits for your ranges.

Before you go multi-node

  • History has to be shared, so clusters need ScyllaDB.
  • Every node needs the same secret_key and cluster_secret. Keep both out of database backups.
  • Leave settings_write_conf off, so the database is the one place admin settings live.
  • Keep the internal ports (:8099, :6699) on a private network.
